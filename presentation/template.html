How a file becomes rows

1. Read the folder like a stream

The job is a Structured Streaming query over the bucket prefix. Each trigger it lists new files, plans them, and hands each batch to one function.

%%C_SCHEMA%% %%C_STREAM%% %%C_TRIGGER%%

2. S3 has no folders

%%C_PREFIX%%

3. The same code runs locally and on AWS

Endpoint, keys and database host come from environment variables. With S3_ENDPOINT empty the job uses real S3 and the AWS credential chain. Checkpoint progress lives in the bucket (%%R_CKPT%%), so a restarted driver resumes where it stopped.

Bad data and replays

These guards exist because uploads are messy. Each one was broken on purpose and the test went red (see Proof).

Replays never duplicate

The same event_id uploaded twice, in any file name, leaves one row. The key is a primary key and the merge skips conflicts (%%R_MERGE%%).

%%C_MERGE%%

Broken lines are quarantined, not fatal

%%C_BADROUTE%%

A pretty-printed message is still one message

Saving one message as indented JSON is the normal way people make a file, and it is the case you asked about. Line by line it looks like seven broken records. The first version of this pipeline rejected it. The fix below re-reads only failing files, whole.

Where the time actually goes

One 81 MB batch took 7.4 s. Changing JDBC connections from 1 to 8 moved it from 7.3 to 7.5 s, so connection count is not the limit. The merge runs inside Postgres on one connection, so no number of executors can speed it up.

Terraform: one module, two environments

Locally the AWS provider talks to MinIO and creates the bucket. In staging the same module also creates a small RDS Postgres. Switching is the provider block and one flag.

%%C_TF_LOCAL%% %%C_TF_RDS%% %%C_TF_GUARD%%

Not applied Staging passes terraform validate and the 0.0.0.0/0 guard rejects as intended. It was never planned or applied because this machine has no AWS credentials. RDS was never exercised, so forced SSL and small-instance speed are unobserved.

What broke while building it

  • Packages set in code were ignored under spark-submit; they are now passed on the command line (%%C_PKG%%).
  • Postgres driver invisible to the JVM's driver manager; it is now loaded through Spark's classloader (%%R_CLS%%).
  • Empty bucket prefix crashed startup. Fixed (see step 2).
  • The Mac's Python path leaked into the pod and the driver died with error=2 (%%R_PY%%).
  • Pretty-printed JSON was shredded into rejects. My first fix used Spark's multi-line reader, which silently ingested 1 of 6 rows from a mixed file. That is why recovery now validates the entire file text.
  • .text() silently reset wholetext, so the "whole file" read was line by line. Now passed as the keyword argument.

Not proven

  • Nothing has run against real S3 or RDS. Local MinIO and Postgres stand in; the code path differs only by environment variables.
  • Kubernetes pods talking to real AWS S3 is not built (it needs an AWS identity inside the pods).
  • Pretty-printed files over 32 MB stay rejected, and a pretty-printed file of several concatenated objects is rejected rather than guessed at.
  • Compressed JSON is not splittable: one file is one task regardless of size.
