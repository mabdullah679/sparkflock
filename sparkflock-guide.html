Sparkflock, in plain English

Read top to bottom. By the end you will know what it does, how to run it, and what is proven versus not.

One sentence: you drop a file of JSON messages into a storage bucket, and about 10 seconds later those messages are rows in a database. Nobody presses a button in between.

1. The big picture

Think of a company mailroom. Letters (your data) get dropped in a tray. A clerk (Spark) checks the tray every few seconds, opens each letter, and files it in the right cabinet (the database). Letters that are unreadable go in a separate "problem" drawer instead of jamming the whole mailroom.

Why "fake" S3 and RDS? So everything runs free on your Mac. Later, the same code is meant to point at real Amazon S3 and RDS by changing settings only, not code. Not yet tried on real AWS

2. The parts

PartWhat it is, simply
MinIOThe bucket. Files land in the folder incoming/.
SparkThe worker. Watches the folder, reads new data, moves it along.
PostgresThe database. Table events = good messages. Table events_rejects = broken ones, with the reason.
TerraformCreates the bucket (and on AWS, the database) from written instructions instead of clicking.
MinikubeA small Kubernetes on your Mac. It lets Spark add and remove workers by itself when a big file arrives.
DockerRuns MinIO, Postgres, and the Spark master/workers as containers.

3. Run it yourself

You need: Docker Desktop, minikube, kubectl, terraform, uv, aws CLI, and Java 21 (brew install openjdk@21). Java 26 does not work with this Spark.

Terminal 1 (open it in the project folder):

1

make init

One time. Installs Spark into a private folder.

2

make up

Starts MinIO and Postgres, creates the bucket.

3

make cluster-up

Starts a Spark master and 1 worker as containers. make cluster-up N=3 gives 3 workers.

4

make stream

Starts the always-on job. Leave it running.

Terminal 2:

5

make gen-one

Makes a file holding one JSON message.

6

make upload FILE=data/one.json

Drops it in the bucket.

7

Wait about 10 seconds, then make count

You should see 1 event. You touched nothing between step 6 and 7. That is the "automatic" part.

Try a big one: make gen-big then make upload FILE=data/big.json (600,000 messages, 80 MB).
Stop everything: make cluster-down then make down.
Prove it works: make test checks 16 things end to end (about 6 minutes) and should end with ALL PASS.
What if the job isn't running?

Nothing happens to new files until you start it. When you do, it catches up on everything it missed.

4. What happens with bad data

  • A line that isn't valid JSON, or has no event_id, does not crash the job. It goes into events_rejects with the reason.
  • A message saved as indented, multi-line JSON (one object, or a list) is accepted as a whole. Indented files over 32 MB are not.
  • Uploading the same file twice does not make duplicate rows. The database merges rows safely, so replays are harmless.

5. Does it add workers by itself?

On plain Spark ("standalone"): No. Measured: with 1 worker, an 80 MB file was handled by exactly 1 worker and the master did not start a second. Workers = whatever you started. A bigger file just gets cut into more pieces and spread over the workers that exist.

On Kubernetes (minikube): Yes. The job asks Kubernetes for more worker pods while work is waiting, and hands them back after 20 idle seconds.

Limit setMeasured result
Max 4 workers1 → 2 → 4 within 10 s, then back to 1 about 20–30 s after work finished
Max 2 workers1 → 2 → 1
make k8s-start            # one time: starts minikube, builds the Spark image
make k8s-test MAX=4       # uploads a big file, watches pods appear then vanish

Dials (in k8s/submit.sh, lines 33–38): MIN_EXECUTORS, MAX_EXECUTORS, IDLE_TIMEOUT. Example: MAX_EXECUTORS=6 k8s/submit.sh stream. How finely a file is sliced is MAX_PARTITION_MB in .env.

If the Spark job fails right after minikube starts

The cluster's name lookup (CoreDNS) is still waking up. Wait, then submit again:

kubectl -n kube-system wait --for=condition=Ready pod -l k8s-app=kube-dns

6. Will more workers make it faster?

Not for the 80 MB file, and it was measured why. Of 7.4 seconds:

Spark writes 1.4 s
Postgres merges rows 4.1 s
other 1.9 s

The merge is a single database job that extra workers cannot share. Repeated runs agreed: max 4 took 17–23 s, max 2 took 18–19 s, no consistent gain. More workers help when files are much bigger or the work per row is heavier. They don't speed up the database.

The "other" slice is simply what's left over from the README's numbers (7.4 − 1.4 − 4.1); it was not separately measured.

7. The live dashboard

A web page that draws your stack as 3D-ish blocks, updating every second: bucket → Spark driver → worker pods → database. It is read-only: it can look at pods but not create or delete anything.

make topo-up      # needs make k8s-start first
open http://localhost:29090
make topo-down

Dotted lines show how things are wired, not how fast data moves. Nothing on this machine measures speed.

Make workers scale: run make gen-big then make upload FILE=data/big.json, and watch 1 worker → up to 4 → back to 1 about 20–30 s after the work ends.

8. What is proven, and what is not

Proven on this Mac (MinIO + Postgres + Spark + minikube)

  • Automatic pickup of new files
  • Replays don't create duplicates
  • Bad data goes to the rejects table
  • Worker counts on the Spark cluster
  • Pods scale up and down on minikube (a real 71 MB upload went 1 → 4 → 2, heading to 1)

Not done

  • Real AWS was never tried. The staging Terraform (terraform/envs/staging) passes terraform validate but was never planned or applied, because this machine has no AWS credentials. The Spark job has never run against real S3 or RDS, which may behave differently (SSL forced, small instances slower).
  • Kubernetes pods talking to real S3 is not built (needs an AWS identity inside the pods).
  • Autoscaling the standalone cluster is not built, and Spark can't do it itself. Use Kubernetes mode.
  • Nobody has seen the dashboard yet. No screenshot, no console-error check, and its drawing code hasn't been mutation-tested. Only its data feed and JavaScript syntax were checked.
  • The browser-console upload script was never run in a real browser.

Next: reconnect the Chrome extension, run the 8-step dashboard checklist in README.txt, break the drawing code on purpose to prove the check catches it, then fix whatever the screenshot shows.

When you do try real AWS (staging, free credits) — not yet tried
  1. Log in to AWS in your terminal.
  2. cd terraform/envs/staging, copy terraform.tfvars.example to terraform.tfvars, fill it in.
  3. terraform init && terraform plan. Read the plan: it makes one S3 bucket and one small RDS Postgres. Then terraform apply.
  4. Copy .env.staging.example to .env.staging, fill from terraform output, then ENV_FILE=.env.staging scripts/submit.sh local --mode once.
  5. When done: terraform destroy. RDS costs money if left running.
